### 关键设计取舍

- **RunnableLambda 只套接口，不改逻辑**：链上第①段就是把 `RetrievalService.search()` 包起来；证据仍然是单元09 从 Chroma 真实查出来的，换了框架不换数据口径。
- **全程用 `assign` 加字段**：`question` 从第②段起一路保留到最后，所以一次 `invoke` 就能同时拿到问题、命中片段、证据文本、来源和答案；换成管道式写法会把问题吃掉，来源就说不清了。
- **证据边界写在 Prompt 里**：「资料为空、或与问题无关时只回答资料不足」是 system 消息的内容，不是代码里的 if；代码只负责把资料递过去。
- **证据门槛是检索层判断，不是正确率**：Top1 余弦相似度低于 0.55 的命中不进 Prompt（本组 7 条资料上实测标定：正当问题 ≥ 0.58，无关问题 ≤ 0.50）。它让「资料不足」有据可查，而不是靠模型自觉；换一批资料必须重新标定。
- **换模型只换第⑤段**：离线摘抄模型与 `ChatDeepSeek` 继承同一个 `BaseChatModel`，`prompt | model | parser` 的连法完全一样，其余五段代码一行不动——这是「链的形状」与「用哪个模型」是两件事的证据。
- **对照的是硬事实，不是措辞**：`key_facts()` 只抽时限数字与资料文件名；任务卡写明无需逐字比较模型措辞，所以结论看的是「两边都提到 7 天、都引用同一个文件」。

- 口头讲解四件事：
  1. **RunnableLambda、ChatPromptTemplate、ChatDeepSeek、StrOutputParser 各自处理了什么** —— 前两个是 Python（取证据 + 编提示词），第三个是唯一调用模型的地方，第四个只做 AIMessage → str 的类型转换。
  2. **为什么用 assign 而不是管道替换** —— 加字段才能把来源一路带到最后；被替换掉的话来源就只剩模型自己写的那句话。
  3. **检索为什么必须由 Python 执行** —— 模型拿不到数据库；链只是把已有的检索函数挂上来，证据出处可核对。
  4. **0.55 这个门槛是什么、不是什么** —— 它是本组 7 条资料上标定的演示值，不是正确率，也不是通用阈值；换资料要重新标。
