## 完成情况（2026-11-02 提前完成，按任务卡日期记在 11-03 日报）

**状态：已完成。** 启动一条命令：`python main.py --serve`，打印装配摘要与两个令牌，页面在 `http://127.0.0.1:8000/`。分层是**接口层 → 业务层 → 数据层**：`app/api.py` 只验身份、收参数、翻译状态码；`app/platform_service.py` 决定这条问题该走哪条路；`app/platform_data.py` 读台账并做权限收窄，`app/platform_store.py` 落四张表。页面是 `web/index.html` 一个文件，零 CDN、零构建步骤。

本单元最关键的一条是**路由不交给模型**。`route_of()` 只用可判定的信号分流：含工单号 `AS\d{5}` → ticket；含订单号 `O\d{6}`（或写成 `SO-2001` 这类台账里没有的格式）→ ticket；含 `EC-FAQ-\d{2}` → faq；问"多少单 / 占比 / 统计" → analysis；其余才走 knowledge。前四类**一次模型都不调**——工单与订单由 Python 读 CSV，FAQ 由 SQLite 参数化查询，统计复用单元23 的固定算子；只有 knowledge 调 1 次模型，且只喂命中的资料。实测耗时把这件事说得很直白：ticket 0 ms、faq 1 ms、analysis 1 ms、knowledge 9 ms（Mock）/ 2.6 s（真实 DeepSeek）。

第二条是**不泄露"存在性"**。客服 A001 问 A002 名下的 `AS23002`，返回的是 `404 未找到可访问的工单`，与"这张工单不存在"同一个结果；权限写进 SQL 的 `WHERE seat_id=?`，不是接口层顺手加个 if。主管 M001 读同一张是 200，管理台 A001 是 403、M001 是 200。

第三条是**数字可复核**。数据看板不直接吐一个数字，而是把单元23 的行数链与算式一起回给页面：「问题类型分布：物流异常 8（25.0%）…共 32 行」「占比 = 该组单数 ÷ 32」「退款合计 5544 元 = 32 行有效数值相加」。看板上每个数字都能拿计算器复算。

### 关键设计取舍

- **路由不交给模型**。让模型自己判断"这是工单问题还是知识问题"看起来更聪明，但工单号、订单号是正则可判定的、FAQ 编号是可判定的、统计意图由关键词可判定——把这几类交给模型，等于给每一次确定性查询都加上一次幻觉风险，还要多付一次调用。现在的做法是：能判定的一条都不调模型，判不了的才进 RAG。
- **查不到就说明"该长什么样"，而不是交给模型说"资料不足"**。订单号写成 `SO-2001` 时，知识库里当然没有这张单，检索只能捞回几条提到"订单编号"的政策片段（实测余弦 0.56，真能答的问题在 0.66—0.73），模型按规则答"资料不足"——用户看到的却是"明明检索到 3 条"。现在的做法：格式不对先从 ticket 路由接住，直接回"台账里是 O + 六位数字（例 O230701）"；页面在 `needs_human` 时把候选列表标题改成"最相近资料（不足以作为依据）"，避免和答复自相矛盾。
- **越权回 404，不回 403**。回 403 等于告诉客服"这张工单存在，只是不给你看"，工单归属就泄露了。统一回 404，并且把权限写进 SQL 的 `WHERE seat_id=?`——权限是查询条件，不是事后过滤。
- **404 给程序，人话给客服**。`/v1/tickets/{id}` 越权仍是 404（HTTP 语义正确，程序好判断）；但 `/v1/chat` 里客服问别人的单，回的是"没找到你能访问的工单 AS23004 …… 可能是号记错了，也可能在别的坐席名下"。同一句话覆盖"不存在"与"无权"两种情况，既不泄露归属，也不会让客服对着一条红色"请求失败"以为系统坏了。
- **四张表分开，审计不存正文**。`turns` 存问答、`audit` 只存路由/耗时/来源数/状态，`feedback` 存评价，`handoffs` 存转人工状态。审计表故意不存问题正文：调用记录是给"查系统做了什么"用的，正文在 `turns` 里，两件事分开才敢给主管看。
- **令牌只放 `sessionStorage`**。放 `localStorage` 会跨标签页和重启一直留着，课堂机器上就是长期可用的凭证。现在关掉标签页就失效，页面重开要重新粘一次。
- **零 CDN**。课堂网络不稳，页面里 `https://` / `http://` / `cdn.` 全为 False，字体用系统字体，图表用 CSS 条形图。有一条测试盯着这三项为 False。
- **业务层不 import FastAPI**。`platform_data / platform_store / platform_service` 只抛 `NotFound` / `BadRequest`，由 `app/api.py` 统一翻译成 404 / 422。这样业务逻辑能用 `unittest` 直接测，不需要起 HTTP。
- **`create_app(context)` 只装配一次**。服务注入用 `dependency_overrides` 指向同一个 `PlatformService`，否则每次请求新建一个 service，台账缓存白做。
- **证据脚本用临时会话库**。闭环那一段如果写进 `.runtime/platform.db`，前一次手工调试留下的 pending 转人工会混进队列，第二天再跑就对不上；改成每次 `TemporaryDirectory` 新建，并且**按 `request_id` 回查那一条**，不看队列首条。
- **旧实现一行没删**。单元24 只新增 `app/api.py`、`app/platform_*.py`、`web/index.html`、`tests/test_unit24.py`、`scripts/generate_evidence_unit24.py` 与三份 CSV；`main.py` 只加了 `--serve` / `--issue-token` / `--init-secret` 与 `/serve` 分支。
