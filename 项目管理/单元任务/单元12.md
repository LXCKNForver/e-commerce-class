### 关键设计取舍

- **格式差异只在一个函数里处理**：`parse_file()` 内部按后缀分三支，出口统一是 `KnowledgeRecord`；上层（入库、计数、回读、检索）完全不知道资料原来是 PDF 还是 CSV。
- **解析单位如实对应人的阅读单位**：Markdown 整篇一条（`document`）、PDF 每页一条（`page`）、CSV 每行一条（`row`），行号从 2 起与表格行号一致；表头不算记录。
- **稳定 ID = 项目 + 文件名 + 位置类型 + 位置**：重跑时 ID 不变，upsert 是更新而不是追加，这是"重跑不重复"的唯一来源。
- **两个项目写进同一个集合，靠 `project_id` 隔离**：不靠分库。ID 带项目前缀 + 每条记录带 `project_id` 元数据 + 查询 `where project_id`，三条缺一条就会被串数据。
- **坏文件不阻断整批**：`load_materials` 逐个文件 try，失败记原因继续跑；但"解析出 0 条"必须报错，不能静默入库一个空批次。
- **回读走数据库而不是源文件**：`read_record()` 用 `collection.get(ids=...)`，证明原文与元数据真的落了盘，而不只是"文件还在磁盘上"。
- **PDF 不做 OCR**：扫描件没有文字层就如实报错，不编一段看起来像正文的内容出来。

### 需要人工完成的部分

- 任务卡要求的**入库前后数量与两条回读截图**需本人截屏（脚本输出已在验收证据里，截图不可替代）。
- 口头讲解三件事：
  1. **三种格式的解析单位** —— 文档 / 页 / 行；PDF 只能按页提文字，扫描件得先 OCR。
  2. **`project_id`、`source`、`location` 各自解决什么** —— 属于谁、来自哪个文件、在这份文件的哪个位置；缺 location 就无法回溯到具体页或行。
  3. **为什么另一个项目不计入本项目数量** —— 不是分了两个库，而是每条记录都带 `project_id`、ID 带项目前缀、查询带 `where` 过滤；换成库里不存在的项目标识就是 0 条。
