## 四、当前选 Chroma 的理由

1. **规模匹配**：约 50—100 条向量，单机完全够用，上分布式是过度设计。
2. **部署成本最低**：`uv sync --extra chroma` 装完就能用，`PersistentClient` 把数据落在
   `.chroma_unit7/`，不需要额外起服务，课堂环境可复现。
3. **与单元06 模型衔接自然**：可以传 `embedding_function=None`，由我们自己调用
   `app/embedding.py` 的中文模型算向量，避免 Chroma 默认模型与课程内容不一致。
4. **运维负担可控**：本组没有专职运维，也没有高并发需求。

## 六、三个指标怎么量（方法论，不是结论）

- **Recall@K**：先用全量遍历算出精确 Top-K 作为标准答案（本单元的
  `InMemoryVectorStore` 就是这个基线）；再用索引查同一批 query，
  统计「索引返回的 K 条里有多少条命中标准答案」，
  `Recall@K = 命中数 / K`。它衡量的是**近似索引丢了多少正确结果**。
- **P95 延迟**：同一批 query 连续跑多次（预热后），把单次查询耗时从小到大排序，
  取第 95 百分位。看 P95 而不是平均值，是为了不掉进「平均很快、偶尔很慢」的坑。
- **存储成本**：`向量条数 × 维度 × 4 字节` 是向量的裸大小，再叠加索引结构、
  原文与元数据的占用。512 维单精度一条向量约 2KB，可据此估算。

**公平测试条件**（换库对比时必须一致，否则数字没有可比性）：
同一批语料、同一个 Embedding 模型与维度、同一份 query 集合、同样的 `top_k`、
同一台机器、同样的索引参数调优投入、预热后再计时。

## 七、HNSW / IVF 原理（口头讲解要点）

- **精确遍历（本单元基线）**：每个候选都算一遍相似度，结果一定准，
  但耗时随数据量线性增长 —— 这就是要引入索引的原因。
- **HNSW（分层可导航小世界图）**：把向量组织成多层「跳表式」的图，
  查询时从最上层快速跳到目标附近，再逐层向下细化。
  特点是查询快、召回高，代价是图结构本身占内存、构建耗时。
- **IVF（倒排文件索引）**：先用聚类把向量分成很多「桶」，查询时只扫最相近的几个桶，
  不必全库遍历。特点是内存友好、构建快；代价是选错桶就会漏召，
  `nprobe`（扫几个桶）越大越准也越慢。
- 两者的共同点：**用一点点召回率换查询速度**，所以才必须量 Recall@K。

## 八、本单元做了什么、没做什么

- 做了：建空集合 `after_sale_knowledge_base`、记录集合 ID 与元数据、
  重复运行核对 ID 不变、用内存实现讲清记录字段与精确检索基线。
